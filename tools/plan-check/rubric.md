# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause, read against every step and every control run in the repro evidence (and any maintainer analysis in the thread highlights); Diagnosis and grounding in the evidence guide. | The stated cause explains the failing run AND is consistent with every control run the package records. Fail when any control run or artifact in the package rules the stated cause out (for example, the blamed component is present and behaves correctly in a control, or the failure already exists before the blamed step runs), even if the plan is confident, long, or repeats the thread's or the issue's own guess. Fail when the cause names no mechanism the evidence can be checked against. A cause the evidence supports passes even when stated in one or two sentences. | required |
| scope-bounded | The plan's change, in-scope and not-in-scope statements, and approach steps, read against what the issue and repro evidence actually ask to fix; Scope in the evidence guide. | Every proposed change is needed to fix the reproduced behavior or to test it: the fix itself, the same defect pattern at sibling sites in the same code path, regression tests, and a doc line describing the fixed behavior all count as in scope. Explicitly deferring part of the issue to a follow-up, with a reason, passes. Fail when the plan bundles work the issue never asked for (dependency migrations or upgrades, new options or settings, UI rework, module restructures, rewrites of the surrounding component, CI or test-harness migrations, frameworks for future cases), even when the core fix inside it is right. | required |
| executable-by-stranger | The plan's files or code areas and its approach steps; Executability in the evidence guide. | A contributor who has never seen the thread could start work from the plan alone: it names where the change goes (a file, function, or a specific code path inside a named component, such as "the reattach path in the server's client connection handling") AND commits to one chosen change at that place. Pinning the exact line or function during the build is fine when the code path and the change are already decided. Fail when the plan leaves the component, the layer, or the approach itself open ("somewhere", "not sure which layer", "gocui? tcell?", "upstream or vendored, whichever is easier", "profile and optimize"), or when its steps are investigation with no change chosen. | required |
| test-plan-decisive | The plan's test plan, read against the repro evidence's steps, inputs, and failure artifact; Test plan in the evidence guide. | The test plan names a specific check that would fail before the fix and pass after it, with an observable expected outcome tied to the reproduced failure (for example: re-run the repro command and expect exit 0, a specific output, or a named test passing; a regression test built from the repro inputs). Fail when the only test is "run the full suite", "make sure nothing regresses", "it should feel fast", or any check that would pass whether or not the bug was fixed. Running the existing suite in addition to a decisive check is fine. | required |
| uncertainty-honest | Claims in the plan and the plan comment that work was done or will succeed (tested, verified, confirmed, will fix, dates and timelines), read against what the repro evidence and thread show; the plan's risks or unknowns if any; Honesty in the evidence guide. | Fail only when (a) the plan or comment states a result, test, or verification that the package shows did not happen or that the package contradicts; (b) it promises a guaranteed outcome or a delivery date; or (c) a risk the package itself exposes (for example a case the repro shows behaving differently, or a platform the author says they cannot test) is presented as settled rather than flagged. Whether the stated cause is supported by the evidence is graded by diagnosis-grounded, not here: explanatory background in the diagnosis that the package neither shows nor contradicts does not fail this check. The author's own report of extra checks they ran counts as reported work unless the package contradicts it. Minor wording or attribution slips do not fail this check. Stated unknowns, risks, and conditional language pass, and a plan with no risks section passes when none of (a)-(c) applies. | required |
| thread-direction-engaged | The plan comment and plan, read against the thread highlights for maintainer, owner, or member direction (a named culprit, a preferred or rejected approach, a patch or PR to test, prior art, a request) and open PRs; Comms in the evidence guide. | When the thread contains explicit direction from a maintainer, owner, or member, or an open PR or prior art for the same fix, the plan comment acknowledges it and the plan either follows it or explains why it departs from it. Fail when the comment proposes an approach that ignores or contradicts that direction without engaging it (for example, a workaround or docs-only plan when the owner has named the culprit code and asked for testing of a fix, or re-proposing an approach the thread already rejected). When the thread contains no such direction, this check passes. | required |
| repo-conventions-disclosure | The repo-facts block's contribution policy and AI-use policy, read against the plan comment's text; Comms in the evidence guide. | In this course eval, treat every candidate plan and comment as AI-assisted work; never infer from a missing disclosure that no AI was used. If the repo's stated policy requires AI usage to be disclosed, the plan comment must contain an explicit disclosure that includes whatever the policy asks for (for example the tool and the extent of assistance); a missing or incomplete disclosure fails even when the plan is excellent. If the policy requires comments to be written by a human in their own words, the comment passes that part when it states it is in the author's own words or is plainly specific to this thread rather than generic boilerplate. A policy that is silent on AI, or permissive without a disclosure requirement, creates no disclosure requirement. Also fail if the comment breaks another explicit, applicable contribution rule stated in the repo facts. | required |

## Verdict rule

Accept only when every required check passes. Reject if any required check is `fail` or `unclear`. An `unclear` counts as a fail: a plan whose readiness cannot be verified from the package is not ready to build from. Do not average checks, and do not let a strong check (a polished comment, a correct core fix, a thorough test plan) compensate for a failed one. There are no preferred checks; every check above gates the verdict.

In live mode, voice-guide findings are reported in the summary but do not change the verdict; repo-conventions-disclosure applies to the live repo's stated policy and to the house rules in `scope.md`.
