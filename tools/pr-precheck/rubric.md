# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | Every changed file and hunk in the diff, read against the plan's stated change, files, in-scope and not-in-scope lines, and deviation notes; Plan fidelity in the evidence guide. | Every hunk in the diff is the planned fix, a test for it, or an artifact the plan or the repo's template names (changelog or whatsnew entry, removing the issue's xfail marker), or is explained in a deviation note. Every change the plan commits to is in the diff, or its absence is stated in the deviation notes or the description. Fail on any unplanned file or hunk (a rewrite of an untouched function, a new option, flag, or setting, a rename pass, a dependency bump) that no deviation note explains, even when the core fix is correct; fail when a planned change is missing with no note. | required |
| description-matches-diff | Every factual claim in the PR title, description, and checklist about what the change does or contains ("implements the plan exactly", "no changes beyond", "no functional changes outside X", "docs updated", "tests added for X", "changelog added"), read against the diff; Plan fidelity in the evidence guide. | Fail when a fidelity or scope claim is contradicted by the diff (the description says "exactly as planned" or "no changes beyond" over unplanned hunks, or says the diff does something it does not), or when a file, doc change, changelog entry, or test the description says was added is absent from the diff entirely. A claimed test case counts as present when an added test asserts that case, even inside a test named for another case. A description that is short but makes no false claim passes. | required |
| repro-before-after | The test evidence, read against the plan's test plan and the issue's reproduction (its failing input, command, and symptom); Test evidence in the evidence guide. | For the issue's failing input, the evidence states what happened before the fix and what happens after it, as printed output or as a specific observation of that same input (for example "before: parse error on line 3; after: matches"). Results written as notes or a summary table count when they are specific to the input. Every distinct failure case the plan's test plan names is re-run the same way, unless the plan's deviation notes and the description say it was deferred and why; controls the plan expects to stay unchanged may simply be stated as unchanged. Fail when the evidence is generic ("tested locally", "works now", "verified on my machine for a day", "colors work now"), re-runs only a control or a path the fix does not change, or leaves out a failure case the plan named with no disclosure. | required |
| repo-checks-shown | The test evidence and the description's testing section, read against the repo's own test or check commands (the template's checklist, the contributing guide, or the plan's test plan); Test evidence in the evidence guide. | The evidence names at least one of the repo's own test commands for the changed area together with its result: printed output, a summary line, or a specific result such as "passes (312 tests)" or "the new integration test passes". A check that failed or could not run passes this check when the failure and its reason are reported. Fail when the repo's own tests are never mentioned as run, or when a checklist box is ticked for a check the evidence says was not run. | required |
| diff-clean | The diff's added and removed lines and the commit list; Diff quality in the evidence guide. | Fail when the diff adds any debris: a debug print or debug logging line, commented-out code or an earlier attempt (including a commented-out debug line), a dead or unused function (including one behind an allow or noqa marker), a new TODO, or a separate hunk or block of pure formatting, re-indent, import-restructuring, or identical re-printed lines that the fix does not otherwise change. One debris item is enough to fail. Lines removed and re-added unchanged inside the same statement the fix edits are diff noise, not debris, and do not fail. Commit messages alone never fail this check. | required |
| template-and-policy | The repo-facts block's PR template asks, contributing instructions, and AI-use policy (live: `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, `scope.md` house rules), read against the PR description and the diff; Standards and comms in the evidence guide. | Every section or checklist item the repo states as required is present with real content: the issue link in the requested form, the checklist answered truthfully, and any artifact the template requires for this kind of change (for example a changelog or whatsnew entry for a bug fix) present in the diff. In this course, treat every candidate PR as AI-assisted work and never infer from a missing disclosure that no AI was used: if the repo's policy requires AI-use disclosure, the description must contain one that gives what the policy asks for (for example the tool and the extent of use); if the policy is silent or permissive without a disclosure requirement, no disclosure is needed. Fail when a required section, checklist, issue link, required artifact, or required disclosure is missing or left as unfilled boilerplate. | required |
| thread-direction | The description and diff, read against explicit maintainer, owner, or member direction in the thread (a question asked, an approach requested or rejected); Standards and comms in the evidence guide. | When a maintainer asked a question or set a direction for this fix, the description answers it or says how the PR follows it. Passes when the thread has no such direction. | preferred |

## Verdict rule

Accept when every required check passes. Reject when any required
check is `fail` or `unclear`: an `unclear` counts as a fail, because a
PR whose readiness cannot be verified from the package is not ready to
submit. The preferred check (`thread-direction`) is reported but never
changes the verdict. Do not average checks, and do not let a strong
check (a correct fix, a polished description, decisive evidence)
compensate for a failed one.

An honestly disclosed shortfall is not a failure: a PR that does less
than its plan, or defers a named case, passes `diff-within-plan` and
`repro-before-after` when the plan's deviation notes and the
description both say what was left out and why.
