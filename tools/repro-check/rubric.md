# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment statements, read against the issue context and repo-facts bug-report requirements; Environment in the evidence guide. | Identifies the tested tool/application version or source revision and operating system, plus installation/runtime/configuration details needed for this trigger or explicitly requested by the repository. A different version/platform is allowed when the difference is stated and the conclusion is limited to the tested environment. Fail when the tested environment cannot be identified, or a material mismatch is silently presented as a test of the original environment. Do not require irrelevant hardware, a commit for a release-only install, or an exact match to the latest release. | required |
| steps-rerunnable | The report's setup, commands or UI actions, input data, flags, and starting state, compared with the issue's trigger; Steps in the evidence guide. | A stranger can repeat the attempt from the described starting state using the supplied inputs and actions or an explicit, accessible reference for unchanged setup. Includes issue-relevant flags, configuration and trigger conditions. Materially changed inputs are identified and justified. Fail for missing essential inputs/actions, vague instructions such as "run the tool," or an altered trigger claimed to be equivalent without support. Do not grade step counts, headings, prose length, or whether commands are numbered. | required |
| observable-evidence | The report's quoted output, traceback, log, screenshot content, test results, or concrete before/after observations; Behavior shown in the evidence guide. | Provides inspectable results tied to the stated attempt, sufficient to check what happened. A specific UI observation or screenshot can be sufficient for a visual bug; a CLI error should include the relevant output or traceback. An attachment claim without its content or an accessible artifact is insufficient. Fail when all that supports the outcome is an assertion such as "confirmed" or "same here." No fixed log length or number of repetitions is required. | required |
| target-behavior | The issue's input and failure signature compared with the candidate report's actual input, command and artifact, not just the candidate's diagnosis; Behavior shown in the evidence guide. | For a reproduced result, the evidence demonstrates the same relevant behavior as the issue, not merely some error in the same tool. If an exit code or exception distinguishes the failure, it must agree with the claimed target. For a cannot-reproduce result, the report shows a faithful attempt at the trigger, the observed non-failure or different outcome, and limits the conclusion accordingly. Fail when a syntax/configuration/setup error, unrelated exception, or different input is called confirmation of the target bug. A transparent failed setup may explain a blocker but is not yet a completed reproduction attempt. | required |
| outcome-honest | Claim and report assertions compared with their supporting artifacts, including expected/actual behavior and uncertainty; Honesty in the evidence guide. | States the expected and observed outcomes and makes no conclusion stronger than the evidence. A supported cannot-reproduce is acceptable. Descriptions of cause that have not been established are labeled as hypotheses. Fail when the text claims success, repeated runs, a confirmed root cause, an attached artifact, or a broader affected population that the package contradicts or does not substantiate. A claim-only draft promises investigation without pretending the planned run already occurred. | required |
| claim-specific-and-constructive | Candidate claim comment against the issue's concrete behavior and both comments' wording; Comms in the evidence guide. | The claim identifies the issue through its behavior, input, component, or other distinguishing detail and states a useful next action or concrete work already evidenced in the full package. Comments communicate actionable information without blaming maintainers, demanding priority, or replacing evidence with generic enthusiasm/assignment requests. A short, plain claim is sufficient; a fixed greeting or experience-level statement is not required. | required |
| repository-conventions | Repo-facts template/contribution/AI-use policy against both comments; live mode also the actual contribution instructions and personal voice guide. | Follows explicit applicable repository requirements, including AI-use disclosure when required. In this course eval, treat candidate comments/reports as AI-assisted work (the instructor gold-label notes establish this premise); do not infer that missing disclosure means no AI was used. If the captured policy requires disclosure, require an explicit disclosure that supplies the tool and extent when that policy asks for them; missing disclosure fails even when the technical report is excellent. An explicit compliant disclosure satisfies this part. Permissive-with-responsibility policies and silence about AI create no additional disclosure requirement. Read new-issue administrative requests (such as confirming a duplicate search) in context: a reproduction comment on an existing issue need not repeat new-issue checkboxes unless the policy explicitly requires them for comments. Required reproduction information may appear in any readable format unless the repository explicitly mandates a format. In live mode, also follows the personal voice rules; in eval mode do not consult that guide. Apply Path Review's parallel-claim rules only in live mode for the scoped classroom repo. | required |

## Verdict rule

Accept when every applicable required check passes. Reject if any applicable required check fails or is unclear. Preferred checks, if added, provide feedback without changing the verdict. Do not average checks or let polished writing compensate for missing proof.

For a claim-only live draft, checks requiring a repro report are unclear with the evidence "not yet applicable: claim-only draft" and are excluded from the verdict. Evaluate the claim's specificity, honesty about planned work, applicable repo conventions, and voice rules. All checks apply to a full package, including every eval bundle. A faithful and evidenced cannot-reproduce can pass every required check; successfully triggering a bug is not an acceptance requirement.
